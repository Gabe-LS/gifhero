## Zero-sensitivity parameters

Several parameters had ZERO measurable effect on any fixture:

- **cropTolerance** (0–20): Identical output for all values on all 3 fixtures. The subframe pipeline's bbox detection is dominated by canvas-staleness (holeTolerance) rather than source-vs-source comparison. On high-motion content (big-buck-bunny), every pixel changes every frame so the bbox is always full-frame. On low-color content (skin-tones), auto-global palette makes the crop identical regardless.
- **temporalWeight** (0–0.7): Zero effect because the subframe pipeline does not use temporal dithering. The flag is only wired to the legacy pipeline. Not a bug — temporal dithering with subframe encoding would interfere with hole punching.
- **palette mode** (local/crossframe/adaptive/global): Zero effect. Imagequant generates per-crop palettes in the subframe pipeline, and the auto-global palette detection overrides the strategy for low-color content. The crossframe strategy adds adjacent-frame data to the quantization pool, but imagequant's adaptive sizing makes the result identical.

## Prose Analysis

### Highest-leverage knobs

1. **maxColors** is the single highest-leverage parameter for file size on complex content. On big-buck-bunny, reducing from 256→16 colors cuts size by 62% (6.0→2.3MB) but drops VMAF by 10 points. The quality knee is at 128 colors (93.7 VMAF, 4.9MB) — diminishing returns beyond that.

2. **lossyLzw** is the most effective compressor. On talking-head, level 4 (the balanced default) saves 11% vs off with just 0.08 VMAF loss. Level 8 saves 26% for 1.0 VMAF loss. Beyond level 10, quality degrades sharply (VMAF < 93 on talking-head at level 15). The sweet spot is 4–6 for quality-oriented encoding, 8–10 for size-oriented.

3. **quantizerQuality** has a clear diminishing-returns curve. Quality plateaus at q80 for all fixtures — going from q80→q100 adds 0.3–1.9 VMAF points but increases size by 15–40%. Below q70, quality drops substantially. The balanced preset's q80 default sits right at the knee.

4. **holeTolerance** is only effective on content with significant static areas. On talking-head (static background, moving face), tolerance=5 cuts size by 21% with 1.2 VMAF loss. On big-buck-bunny (full-motion), no effect at all — every pixel changes every frame.

### Counterintuitive findings

- **quantizerSpeed 8–10 increases VMAF.** Faster imagequant produces different (noisier) palettes that score higher on VMAF. On big-buck-bunny: speed 1 = 95.07 VMAF/6.0MB, speed 10 = 95.89 VMAF/6.4MB. The extra 400KB of file size comes from the palette diversity, but VMAF rewards the slightly different dithering pattern. This suggests imagequant at speed 1 may over-optimize for spatial quality at the expense of temporal consistency that VMAF captures.

- **quantizerQuality 100 is SLOWER than q90 but not better.** On talking-head, q100 yields 97.48 VMAF (worse than q90's 97.69) because maximum quality forces imagequant to spend extreme time on precision that produces more uniform dithering, which VMAF penalizes slightly for temporal flicker.

### Recommended preset defaults

Based on the sensitivity data, the current balanced preset defaults are well-positioned:

| Parameter | Current | Recommendation | Rationale |
|-----------|---------|----------------|-----------|
| cropTolerance | 5 | 5 (no change) | Zero sensitivity; value doesn't matter |
| holeTolerance | 0 | 0 (no change) | Higher values trade quality for size; 0 is safest default |
| quantizerQuality | 80 | 80 (no change) | Right at the quality knee |
| quantizerSpeed | 3 | 3 (no change) | Good balance; higher speeds increase file size |
| lossyLzw | 4 | 4 (no change) | Minimal quality loss, meaningful compression |
| maxColors | 256 | 256 (no change) | Maximum quality; lower values for size-oriented presets |

### Content-adaptive opportunities

1. **Motion-based holeTolerance**: Low-motion content (< 30% pixels changing per frame) benefits from holeTolerance=3-5. High-motion content should keep holeTolerance=0.

2. **Color-complexity-based maxColors**: The auto-global palette already handles < 64 colors. For the 64–128 range, maxColors=128 would save significant size with minimal quality loss on photographic content.

3. **Size budget-based lossyLzw**: If the user specifies a target file size, lossyLzw can be dynamically adjusted. The VMAF/size curve is predictable: each lossyLzw increment saves roughly 5-8% file size at 0.5-1.0 VMAF cost.

# Comparison with gifski

## Per-fixture analysis

### skin-tones (few colors, slow motion)
- **gifski**: 284KB, 256-color local palettes, aggressive sub-framing (260×116 to 269×183), disposal method 1
- **gifhero**: 364KB (+28%), 32-color trimmed palettes, consistent 266×180 sub-frames, disposal method 0
- **Gap cause**: gifski's adaptive sub-frame sizing is much more aggressive (smallest: 260×116 vs gifhero's fixed 266×180). gifski varies LZW data 2.3–13.7KB/frame while gifhero is uniform at ~6.1KB/frame. gifski captures that frames differ only in the face region and crops tightly; gifhero's bbox detection includes the full body consistently.

### talking-head (photographic, static background)
- **gifski**: 2.0MB, sub-frames down to 465×270 (crops static left margin), 256-color palettes, avg 33.7KB/frame LZW
- **gifhero**: 2.4MB (+20%), NO sub-framing (all frames 480×270), 128-color palettes, avg 41.6KB/frame LZW
- **Gap cause**: gifhero fails to crop the static background. Despite using the subframe pipeline, every frame outputs at full canvas size (480×270). This is because the stale canvas check forces every pixel to re-encode. gifski's sub-framing saves ~22% on talking-head. Additionally, gifhero uses 128-color local palettes vs gifski's 256 — the palette trimming is too aggressive, removing colors that would improve LZW compression.

### big-buck-bunny (complex, fast motion)
- **gifski**: 4.2MB, full-frame (480×270), transparency on 59/60 frames, 256-color palettes, avg 72.5KB/frame LZW
- **gifhero**: 6.0MB (+43%), full-frame (480×270), NO transparency (0/60 frames), 256-color palettes, avg 103.8KB/frame LZW
- **Gap cause**: This is the largest gap and the most critical. gifski punches transparent holes on EVERY frame (59/60), achieving avg 72.5KB/frame LZW. gifhero produces fully opaque frames at 103.8KB/frame — 43% more data per frame. The root cause: gifhero's stale-canvas check (`palCanvasDiff > 3`) is too conservative on high-motion content with per-frame palettes. Each frame's palette differs enough that the stale check flips nearly every transparent pixel back to opaque, negating the entire hole-punching step.

## Summary

| Fixture | gifski | gifhero best | Gap | Root cause |
|---------|--------|-------------|-----|------------|
| skin-tones | 284KB | 364KB | +28% | Bbox too wide, LZW less efficient |
| talking-head | 2.0MB | 2.4MB | +20% | No sub-framing (stale canvas prevents cropping) |
| big-buck-bunny | 4.2MB | 6.0MB | +43% | Zero transparency (stale check negates hole punch) |

## Key architectural difference

gifski uses a **shared global palette** across all frames, meaning the stale canvas check rarely triggers — when frame N's palette color for a pixel is the same as frame N-1's, the canvas is never "stale." gifhero uses **per-frame local palettes**, so palette colors shift between frames, making the canvas appear stale even when the underlying content hasn't changed. This is the fundamental source of the size gap on high-motion content.

The fix would be either:
1. Use shared/global palettes for high-motion content (detecting motion level during the probe phase)
2. Make the stale check palette-aware: compare source-to-canvas distance relative to the current frame's palette precision, not a fixed threshold
3. Accept some visual error in the stale check for frames with substantially different palettes

# Parallelization

WASM imagequant serializes internally — parallel encoding yields 1.0× speedup (no benefit). All 192 encodes ran effectively sequentially. This is a known limitation of single-threaded WASM modules in Node.js; worker threads would be needed for true parallelism.
